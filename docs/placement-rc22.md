# RC22 placement update

All block placement users of PlacementManager now select a point on the clicked block's outline and check that same point before submitting. A wall-range exception applies to the actual world ray and cannot exceed normal reach. Floating placement remains explicitly allowed by existing generic callers; AutoAnchor exposes AirPlace and WallRange. These are client-side checks, not a guarantee that a server accepts air placement or teleport movement.

Affected direct paths: AutoCrystal, AutoAnchor, AutoBed (including TpMode), PistonCrystal, GuangxiTP, AutoPortal and Bomber. Surround, AutoTrap, PearlBlocker, Scaffold and AutoMine glass inherit the shared geometry and final submission checks. Existing font fallback and licensing remain part of both build trees.

Crystal placement uses per-call range/sneak options and checks a two-block-high entity column, matching the local Minecraft 1.21.11 EndCrystalItem bytecode. FacePlace still lowers the damage threshold for eligible targets; EntityOverlap is a separate, disabled-by-default compatibility option for servers that permit a living target inside that column. Ordinary dropped items and existing crystals are blockers. Rotation rejection prevents a placement from being recorded as submitted.

TP crystal and bed validate from the eye position corresponding to the synthetic movement. A cancelled movement skips the dependent interaction. Cancellation or an exception during interaction still restores movement. Local packet submission is never treated as a server acknowledgement. TNT ignition waits for observed TNT; AutoPortal clicks the frame support and waits for an observed portal before reporting completion.

PistonCrystal ReuseRedstone now preserves existing redstone blocks in place. Eligible layouts with existing power are preferred after damage/reach/self-safety validation and require no replacement redstone item. The module scans both normal adjacent-piston layouts and gap-two layouts: the latter let a piston be placed after a confirmed crystal without intersecting the crystal's two-block-wide entity bounds. It predicts the shorter head-sweep push (about 0.51 blocks in an unobstructed vanilla layout) for damage selection and waits for observed movement toward the target before attacking. The sequence is base -> confirmed crystal -> piston -> existing power -> observed push -> attack. Power loss aborts; it never silently places or mines redstone on that path.

An existing correctly oriented piston in a reusable gap-two layout may be recycled with an owned one-shot PacketMine operation. This requires enabled/available PacketMine, a free primary operation, mining reach and a replacement piston. It mines only that piston, waits for observed air in both the piston and old head cells, then runs the crystal-first sequence. Unknown replacement blocks abort. The owned operation clears on observed air so rebreak cannot destroy the newly installed piston. Manual retargeting relinquishes ownership, and cleanup cannot cancel another target. Existing redstone beside a tight adjacent-piston layout is not treated as a universally reusable setup: that geometry cannot accept a fresh piston after the crystal spawns; the scanner looks for another feasible layout. Redstone torches/dust and quasi-connectivity are outside this redstone-block reuse path.

Validation includes existing combat/licensing regressions plus negative coordinates, world-edge coordinates, slab/bed-sized outlines, exact/outside/nonfinite reach, mutable block positions, cancelled movement, rejected interactions, exception cleanup, retained-power planning, four-direction crystal/piston collision, delayed head removal, vanished power and observed push. Offline startup checks validate client initialization; multiplayer timing, anti-cheat acceptance, and combat effectiveness require live server testing.

Hachimi is used as analysis evidence only. Its Java wrappers show aggressive sequential anchor attempts; the native Fg implementation and runtime JNI registration are still unrecovered. No hypothetical native body is presented as recovered code or copied into the client.
